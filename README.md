# Защищённый REST API

Лабораторная работа 1 по дисциплине «Информационная безопасность». Автор: Руссу Алексей Иванович, группа P3417, Университет ИТМО, 2026.

Приложение регистрирует пользователей, выдаёт JWT после проверки пароля и возвращает профиль текущего пользователя. Стек: Java 21, Spring Boot 4.1.2, Spring Security, Spring Data JPA/Hibernate, H2 2.5.252, Maven. Данные сохраняются в локальной базе `data/secure-api`; консоль H2 отключена. Версия H2 явно обновлена относительно BOM Spring Boot. После первоначального SCA стек обновлён до Spring Boot 4.1.2 для устранения обнаруженных уязвимостей зависимостей.

## Запуск

Требуются JDK 21 и Maven 3.9. Из корня проекта выполните `mvn verify`. Перед запуском задайте два независимых случайных секрета. Пример для PowerShell 7:

```powershell
$env:JWT_SECRET = [Convert]::ToBase64String(
  [Security.Cryptography.RandomNumberGenerator]::GetBytes(48))
$env:DB_PASSWORD = [Convert]::ToBase64String(
  [Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
java -jar target/secure-rest-api-1.0.0.jar
```

В Bash можно использовать `export JWT_SECRET=$(openssl rand -base64 48)` и `export DB_PASSWORD=$(openssl rand -base64 32)`. При повторном запуске существующей базы используйте прежний `DB_PASSWORD`. В рабочем окружении храните секреты в менеджере секретов. Не добавляйте их в Git. JWT_SECRET короче 32 байт не принимается; безопасное значение следует именно генерировать случайно.

Адрес учебного сервера: `http://127.0.0.1:8080`. Сервер слушает только loopback. Для доступа по сети требуется отдельная настройка HTTPS на обратном прокси. Смена JWT_SECRET делает ранее выданные токены недействительными.

## Описание API

### POST /auth/register

Третий метод задания — регистрация. Тело запроса:

```json
{"login":"student","password":"Example-Lab-Password-2026!","displayName":"Алексей"}
```

Логин: 3–32 символа, латинские буквы, цифры, `_`, `.` и `-`. Пароль: не менее 12 символов и не более 72 байт UTF-8, поскольку используется bcrypt. Имя: 1–100 символов. Ответ `201 Created` содержит `id`, `login`, `displayName`; пароль и хэш не возвращаются. Повторный логин даёт `409 Conflict`, неверные поля — `400 Bad Request`.

### POST /auth/login

```json
{"login":"student","password":"Example-Lab-Password-2026!"}
```

При верных данных возвращается `200 OK` и объект с полями `accessToken`, `tokenType` (`Bearer`), `expiresIn` (`900` секунд). При неверном логине или пароле возвращается одинаковый ответ `401 Unauthorized` с `{"error":"Invalid credentials"}`. Для отсутствующего пользователя тоже выполняется проверка bcrypt по техническому хэшу, что уменьшает различие времени ответа.

### GET /api/data

Передайте `Authorization: Bearer <accessToken>`. Успешный ответ `200 OK` — массив из профиля владельца токена. Чужие профили не возвращаются. Без токена, с повреждённым или просроченным токеном сервер отвечает `401 Unauthorized`.

## Проверка с curl

Следующие команды предназначены для Bash; пароль в примере используется только для учебной проверки. Сначала сохраните запросы в файлы:

```bash
cat > register.json <<'JSON'
{"login":"student",
 "password":"Example-Lab-Password-2026!",
 "displayName":"Student"}
JSON
cat > login.json <<'JSON'
{"login":"student","password":"Example-Lab-Password-2026!"}
JSON
curl -i -H 'Content-Type: application/json' \
  --data-binary @register.json http://127.0.0.1:8080/auth/register
curl -H 'Content-Type: application/json' \
  --data-binary @login.json http://127.0.0.1:8080/auth/login
curl -i http://127.0.0.1:8080/api/data
curl -i -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/api/data
```

В последней команде переменная `TOKEN` должна содержать значение `accessToken` из ответа входа. Пример его получения с `jq`:

```bash
TOKEN=$(curl -s -H 'Content-Type: application/json' \
  --data-binary @login.json \
  http://127.0.0.1:8080/auth/login | jq -r .accessToken)
```

## Реализованные меры защиты

**SQL-инъекции.** Методы Spring Data JPA `findByLogin` и `findById` формируют параметризованные запросы. Пользовательские значения передаются как параметры, без конкатенации SQL. Ограничение уникальности логина находится в базе, поэтому одновременная регистрация также не создаст дубликат. Тест с логином `' OR 1=1 --` проверяет отказ во входе и сохранность таблицы.

**XSS.** Перед включением строк пользователя в DTO вызывается `HtmlUtils.htmlEscape`. Например, `<script>alert(1)</script>` возвращается как `&lt;script&gt;alert(1)&lt;/script&gt;`. Исходное значение хранится в базе; экранирование выполняется при каждом формировании ответа. API возвращает JSON, Spring Security добавляет `X-Content-Type-Options: nosniff`. На клиенте данные всё равно следует вставлять через `textContent`, а не `innerHTML`: HTML-экранирование не является универсальной защитой для JavaScript, URL и других контекстов.

**Пароли.** `BCryptPasswordEncoder(12)` создаёт адаптивный хэш со случайной солью; соль и параметр сложности входят в строку хэша. Даже одинаковые пароли дают разные строки в базе. Хэши никогда не включаются в ответ API. Поля запроса проверяются через Jakarta Validation; отдельно ограничивается длина пароля в байтах UTF-8, чтобы исключить молчаливое усечение bcrypt.

**JWT и разграничение доступа.** Spring Security проверяет Bearer-токен до вызова защищённого метода. Разрешён только HS256; алгоритм не выбирается по недоверенному содержимому токена. Проверяются подпись, `iss`, `aud`, `sub`, `iat` и `exp`. Токен действует 15 минут и содержит числовой идентификатор пользователя, издателя, аудиторию и временные отметки. Пароль и конфиденциальные данные в JWT не помещаются: JWT подписан, но не зашифрован. Профиль выбирается по `sub`, поэтому клиент не задаёт идентификатор другого пользователя.

**Состояние и ошибки.** Сессии, form login и HTTP Basic не используются. Аутентификация принимается только из явно установленного заголовка Authorization, а не из автоматически отправляемой cookie. CSRF-защита остаётся включённой; исключения сделаны только для двух открытых JSON-методов регистрации и входа. GET не изменяет состояние и не требует CSRF-токена. При переходе к cookie-аутентификации эти исключения необходимо пересмотреть. Ошибки валидации и базы возвращаются без SQL, пароля и стека вызовов. JSON с токеном получает стандартный запрет кеширования Spring Security.

## Автоматические проверки

```bash
mvn -B -ntp verify
mvn -B -ntp spotbugs:check
mvn -B -ntp dependency-check:check
```

Тесты JUnit/MockMvc проверяют успешный сценарий, ошибки регистрации, ограничения пароля, SQLi, XSS, запрет доступа без JWT, подмену подписи, истечение токена, издателя и аудиторию, обязательность срока действия и изоляцию данных пользователей.

SAST: SpotBugs 4.10.5.0 с Find Security Bugs 1.14.0 анализирует скомпилированный код. Фильтр `config/spotbugs-security.xml` выбирает категорию SECURITY и исключает только информационный детектор SPRING_ENDPOINT, который перечисляет маршруты, а не уязвимости. Это проверка безопасности, а не всех замечаний качества кода. Отчёт: `target/spotbugsXml.xml`.

SCA: OWASP Dependency-Check 13.0.0 анализирует зависимости по опубликованным сведениям об уязвимостях. Сборка завершается ошибкой при CVSS ≥ 7 или невозможности завершить анализ. Отчёты: `target/dependency-check-report.html` и `.json`. Анализатор OSS Index отключён, поскольку требует отдельной авторизации; NVD и остальные применимые анализаторы остаются включёнными. Отсутствие находок означает отсутствие известных совпадений в используемой базе на момент проверки, а не доказательство абсолютной безопасности.

База NVD загружается из официальных JSON 2.0 feeds через параметр `nvdDatafeedUrl`; ключ API не требуется. Это также обходит подтверждённую ошибку Dependency-Check 13.0.0 при работе без ключа через API (issue #8715 в репозитории DependencyCheck). При первичной загрузке сканер получает большую базу CVE; это может занять более 20 минут. В CI используется кеш базы. Актуальность определяется метаданными официального источника NVD.

## GitHub Actions

Workflow `.github/workflows/ci.yml` запускается при каждом `push`, `pull_request` и вручную через `workflow_dispatch`. Задание `test-and-sast` собирает проект, выполняет тесты и SpotBugs. Задание `sca` запускает Dependency-Check независимо. При ошибке проверка остаётся красной: `continue-on-error` не используется. XML/HTML/JSON-отчёты сохраняются в Actions Artifacts даже при неуспешном анализе, если сканер успел их создать. Токен workflow имеет только `contents: read`.

После публикации откройте вкладку Actions, дождитесь зелёного запуска обоих заданий и скопируйте постоянную ссылку на конкретный запуск. Для отчёта нужны скриншоты шагов SpotBugs и Dependency-Check именно из этого запуска.

## Границы учебной реализации

В проект не входят блокировка перебора паролей, MFA, отзыв отдельных JWT, refresh-токены и автоматическое развёртывание на сервер. Перед промышленным использованием нужны HTTPS, ограничение частоты запросов, мониторинг, ротация ключей и миграции базы. Здесь pipeline выполняет сборку и проверки безопасности; деплой не настроен.
